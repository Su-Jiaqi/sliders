# Headline LPIPS (0.2166) vs. seed-stability mean (0.2201±0.0004) — real gap, root cause found — 2026-07-25

## The problem

`tab:app_seed_stability`'s three seeds (42/43/44) average LPIPS 0.2201±0.0004, ~9
standard deviations away from the headline production number (0.2166) quoted
elsewhere in the paper (Table 1, `table1_significance.md`). Too large and too
consistent-in-direction to be explained by the documented seed-noise floor alone.

## Where the headline 0.2166 comes from

Traced to `logs/ablation-2/run_socalfire_scale1_ablation_eval.sh` (2026-05-03),
which symlinks `outputs/refine-2/socalfire/test/scale1` (unmodified, current
production output) and evaluates it — `outputs/eval/ablation/socalfire_scale1_compare_full/refined/socalfire-infered_metrics.csv`:
LPIPS=0.21660283650082301, SSIM=0.5953810033072361, PSNR=23.806210092130513
(exact match to the paper's quoted 0.2166/0.5954/23.8062). This is genuinely the
production pipeline's own number, not a different checkpoint mix-up like the earlier
CAS-classifier findings.

## Root cause: the base-diffusion generation for the seed-stability sweep ran in a different, partially-broken software environment than the headline run

Traced `outputs/refine-2/socalfire/test/scale1`'s base (pre-refiner) images to
`outputs/infer/socalfire/test/scale1`, generated by `infer/run_socalfire_scales.sh`
on **2026-04-21** (confirmed via file mtimes, one single continuous run that day).
The seed-stability sweep's base images (`outputs/stability/socalfire_seed{42,43,44}/infer/`)
were generated fresh on **2026-05-04** — not reused from the April 21 batch.

Its log (`outputs/stability/socalfire_seed42/logs/01_infer.log`) shows:
```
WARNING[XFORMERS]: xFormers can't load C++/CUDA extensions. xFormers was built for:
    PyTorch 2.10.0+cu128 with CUDA 1208 (you have 2.11.0+cu130)
  ... Memory-efficient attention ... won't be available.
```
i.e. sometime between 2026-04-21 and 2026-05-04, PyTorch/CUDA were upgraded on this
machine, silently breaking xFormers' compiled kernels — every run after the upgrade
(including the seed-stability sweep, and the **current** environment: verified this
exact same warning still fires today) falls back to a different, non-accelerated
attention implementation. This changes the UNet's numerics even at an identical
nominal seed.

Confirmed this actually produces different images, not just a theoretical concern:
direct LPIPS distance between the April-21 base image and the May-4 "seed=42" base
image (`infer/batch_infer_xbd_paired_scales.py` defaults to `--seed 42`, so this is
the closest possible apples-to-apples pair), computed on cuda:5, 60 test images:
**mean LPIPS = 0.0771** — far larger than what a truly deterministic rerun at the
same seed should produce.

A second, independent complication: the LoRA checkpoint path the headline script
(`infer/run_socalfire_scales.sh`) references —
`output-models/lora/xbd_paired_slider_endpoint_paired_alpha16.0_rank16_full_last.safetensors`
— **no longer exists anywhere on this machine** (`output-models/lora/` itself is
gone). A same-configuration file with a different name,
`output-models/train/socalfire_slider_paired_alpha16.0_rank16_full/socalfire_slider_paired_alpha16.0_rank16_full_last.safetensors`,
exists and is contemporaneous (2026-04-20), plausibly the same weights under a later
directory reorganization — but this can't be confirmed byte-for-byte, and no surviving
script records which `--lora_path` the seed-stability sweep actually used (its
driving script no longer exists; only the raw logs survive, which don't echo argv).

The refiner network itself (`unified_refiner_scale1stronger`) is confirmed to be the
same, shared checkpoint across both runs (already established in the prior
seed-stability investigation via image-level LPIPS: seed42's *refined* images sit at
0.0100 LPIPS from current production vs. 0.0459 from the old refine-1 pipeline —
clearly same pipeline family). So this is specifically a **base-generation-stage**
environment/checkpoint provenance issue, not a refiner or classifier issue.

## Bottom line

This is a **real, mechanistically-explained gap**, not measurement error and not
pure seed noise: the headline number and the seed-stability numbers were not
produced by a reproducible, single, consistent software environment. It is a
different bug class from every classifier-leak finding earlier this project — this
one is about the base diffusion generation step, and affects LPIPS/SSIM/PSNR
directly (not just CAS).

**No clean substitute already exists** (unlike the classifier-leak fixes, there is
no alternate already-computed csv to swap in). The only way to actually reconcile
the two numbers is to regenerate both in a single, consistent environment — which
would require either fixing the xFormers/PyTorch version mismatch (a real
environment change, not something to do without sign-off) or accepting the current
eager-attention fallback and **regenerating the headline production run** to match
it (also a real, visible change to Table 1's own numbers, not something I did
unprompted). Did not attempt either — reporting only, per "just check the source, same
as before." All checking was done on `cuda:5` (idle at the time); `cuda:0` was not
touched.

## Recommended framing for the paper

Do not silently swap either table's numbers to match the other. Two honest options:
1. Disclose the environment-drift caveat explicitly in the seed-stability section
   (the three seeds are internally consistent with each other, just not with the
   separately-generated headline run) — cheapest, no regeneration.
2. Regenerate the headline Table 1 numbers using the same environment/seed used for
   the stability sweep (or vice versa) for full reproducibility — more correct, but
   is new GPU generation work and a decision that changes a load-bearing number in
   the paper, so needs your go-ahead before I touch anything.
