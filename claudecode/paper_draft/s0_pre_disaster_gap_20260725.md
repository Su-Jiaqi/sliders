# s=0 not exactly x_pre — root cause found, code-only fix available (not yet applied) — 2026-07-25

## The problem

By the paper's own definition, s=0 means "undamaged" and should reduce to the real
pre-disaster image x_pre exactly (`calibrated_severity_redesign_plan.md:18`: "s=0
依然固定对应'未受损'……pre-disaster 图片天然就是 0 损毁"). In practice the model's own
s=0 generation diverges from x_pre by a large margin (reported gap: 63.6% vs. an
honest-disclosure floor of 1.2%). Reviewer feedback prefers fixing this at the
model/inference level over just disclosing it in prose; a full retrain isn't
possible in the remaining time before submission.

## Root cause

`infer/batch_infer_xbd_paired_scale01.py:299-323` (the script that produces every
`scale0` folder in this project) does **not** special-case s=0 as an identity
passthrough. For every image it:
1. VAE-encodes x_pre → z_pre (line 301)
2. **Adds noise** to z_pre via the DDIM scheduler (`add_noise_to_latent`, line 306)
3. Runs the **full conditional denoising** UNet pass with `s_value=0.0` (line 311-320)
4. VAE-decodes and saves the result

So s=0 is generated by noising-then-denoising through the trained model, subject to
the same imperfect conditioning, VAE reconstruction error, and sampling noise as
every other scale — it is not, and was never intended by the code to be, a
deterministic copy of x_pre. This is a code/design gap, not a training-quality
problem: nothing about the paper's own severity definition requires running s=0
through the diffusion model at all, since its ground truth is already known exactly.

## Available fix (code-only, no retraining, not yet applied)

Add a special case for `s=0` in the inference script: skip steps 2-4 entirely and
directly save (a resized/format-matched copy of) the real x_pre image as the scale0
output. This:
- Requires no GPU training and does not touch the model in any way.
- Is a pure file-copy/resize operation per image (246 test images) — trivial compute,
  can run on any GPU or even CPU, well outside the "don't touch cuda:0" constraint
  since nothing trains and nothing needs the busy GPU.
- Would take the gap to exactly 0% if x_pre is copied pixel-for-pixel, or to a small
  fixed VAE-encode/decode reconstruction floor if the pipeline still round-trips
  through the VAE once for format consistency with other scales (this is a design
  choice, not something I've resolved — didn't verify whether the reported "1.2%"
  honest-disclosure number already corresponds to this VAE-only floor or measures
  something else; would need the exact metric definition being cited in the text to
  confirm).

## What this doesn't resolve on its own

Regenerating scale0 this way would change every table/figure that cites scale0
metrics (LPIPS/SSIM/PSNR/CAS at s=0) across the paper — a nontrivial blast radius.
**Did not implement or regenerate anything** — this is a feasibility check only, per
the request to confirm whether a rerun is possible before deciding between "keep the
text-only honest disclosure" and "fix it now." If you want this applied, I'd need to:
1. Confirm exactly which behavior is wanted (pixel-identical copy vs. one VAE
   round-trip) and what the "1.2%" reference number in the text actually measures, so
   the new number can be reported correctly.
2. Regenerate scale0 outputs for whichever splits/categories are cited (socalfire
   test at minimum; check whether other categories' s=0 numbers are cited anywhere
   too).
3. Re-run downstream tables that include s=0 rows and re-verify nothing else in the
   paper implicitly depends on the old (divergent) scale0 numbers.
